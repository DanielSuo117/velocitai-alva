# 落库校验规则（P0.8–P0.10）

**触发**：准备把经验 / 规则 / 项目事实写入 `.claude/skills/` / `.claude/rules/` / `docs/`，或修改 `CLAUDE.md` 路由表时。

自我进化机制写入的内容会被**每一个新会话加载为高优先级上下文**。垃圾数据在这套架构里不是静态污染，而是会自我强化的负反馈 —— 写错一次，之后每次编码都被它带偏。本规则是落库前的闸门。

---

## P0.8 · 沉淀前必须先检索去重

**触发**：准备新增规则条款或新建 skill 时。

**规则**：先检索 `.claude/rules/` 与 `.claude/skills/` 中的既有内容。已有同主题条款的，必须合并进原文件，禁止另起炉灶。

❌ 反例：遇到定位符超时问题，直接新建 `.claude/rules/playwright/timeout-new.md`，而 `timeout-and-wait.md` 已经在讲同一件事 —— 两份规则从此各说各话，agent 读到哪份全凭运气。

✅ 正例：先 grep「超时」，发现 `timeout-and-wait.md` 已覆盖，把新踩的坑作为一个 ❌/✅ 例子追加进该文件对应条款。

---

## P0.9 · 沉淀必须带触发条件与失败现象

**触发**：写入任何规则条款时。

**规则**：每条规则必须写明 `**触发**：<什么情况下适用>`，并附真实踩坑的失败现象。没有触发条件的规则等于没有证据，禁止落库。推测、一次性结论、通用常识一律不写。

❌ 反例（示例条目，非本文件真实条款）：

```markdown
**大文件上传要多等一会**

上传大文件时适当加长超时时间，避免断言过早失败。
```

既没有触发条件，也没有失败现象，更没有可执行的判定标准（"适当加长"是多少？）—— agent 读了不知道何时该适用、该改哪个参数。

✅ 正例：

```markdown
**大文件导入必须显式传 timeout，隐式默认值不够用**

**触发**：断言目标是"导入完成"提示，且上传文件 > 20MB。

**失败现象**：用默认的 `DEFAULT_TIMEOUT=15000` 断言导入结果，服务端处理耗时超过 15 秒，
断言在文件还在处理时就超时失败，而不是因为功能真的坏了。

❌ `self.is_visible(IMPORT_DONE_TOAST)`
✅ `self.is_visible(IMPORT_DONE_TOAST, timeout=60000)`
```

---

## P0.10 · 新建 skill / rule 必须先提案

**触发**：要在 `.claude/skills/` 或 `.claude/rules/` 下新建文件（而非在已有文件中追加）时。

**规则**：先向用户提案，说明四项：触发条件、失败现象、拟写入位置（为何是新建而非并入已有文件）、检索结果（与哪条既有规则相关）。获确认后才写。在已有文件中追加 ❌/✅ 例子、修正笔误、更新 `docs/` 事实清单，不受此限。

❌ 反例：排查完一个 bug，直接 Write 一个 `.claude/skills/new-debug-trick/SKILL.md`，用户毫不知情，路由表也没登记 —— 成为一个谁都不会去读的孤儿文件。

✅ 正例：向用户说明「这次踩的坑是 X，触发条件是 Y，既有的 quick-debug 没覆盖分支 Z，建议新建还是并入 quick-debug？」，由用户决定。

---

## P0.11 · 证据必须可核验，不得只写「已验证」

**触发**：向 `.claude/rules/` 写入新条款，或改写既有条款标题时（改标题 = 改规则本身，须重新给证据）。

**失败现象**：P0.9 要求写触发条件与失败现象，但闸门此前只检查 `**触发**` 这几个字是否出现 —— `**触发**：无` 原样放行。实测本仓库 45 个条款中只有 5 个写了失败现象、0 个给出可核对的验证：形状全部合规，证据成色却无从判断，实测得来的规则与顺手推测的规则在后续会话里享有同等优先级。

**规则**：条款须写明失败现象，并在 `**验证**` 里给出至少一个**可被机器核对**的引用 —— 用例 `tests/x.py::TestY::test_z`、代码位置 `framework/pages/x.py:42`，或修复的 commit 短哈希。闸门会用 AST 解析源码、用 `git cat-file` 核对哈希：引用的对象不存在即拦截。「已验证过」「跑通了」不算证据；写不出引用，说明这条规则尚未被验证，先验证再落库。

**验证**：`.claude/hooks/gate/tests/test_provenance.py::TestReferenceMustExist::test_fabricated_test_name_blocks` —— 编造的用例名、编造的 commit 哈希、空话式验证在实测中全部被拦下，证据齐全者放行。

❌ 反例：

```markdown
**触发**：视情况
**失败现象**：无
**验证**：已验证过，跑通了
```

三行全是形状合规的空话：读到这条规则的会话无从判断它是实测结论还是顺手推测。

✅ 正例：

```markdown
**触发**：断言目标是「导入完成」提示，且上传文件 > 20MB。
**失败现象**：用默认超时断言导入结果，服务端处理耗时超过上限，断言在文件还在处理时
就超时失败，而不是因为功能真的坏了。连续 3 次复现。
**验证**：tests/test_import.py::TestImport::test_large_file
```

## 违规码速查

闸门脚本是 `.claude/hooks/gate_cli.py`，经 `.claude/settings.json` 的 `hooks` 接在 Write/Edit、`git commit` 前与每轮 Stop 时。收到拦截时，读 `permissionDecisionReason` 里的违规码，按下表对照修改。

| 码 | 含义 | 修法 |
|---|---|---|
| STR001 | SKILL.md 缺 frontmatter 或缺 name/description | 缺整个 frontmatter 时补 `---` 块；缺字段时补齐 `name` / `description` |
| STR002 | frontmatter `name` 与目录名不一致 | 把 `name` 改为目录名 |
| STR003 | 规则文件缺 ❌ 反例或 ✅ 正例 | 为每条规则补一组 ❌/✅ 代码块 |
| STR004 | Markdown 链接指向不存在的路径 | 修正相对路径层级，或补上目标文件 |
| STR005 | 文件超过 300 行 | 建议拆分（仅提示，不阻断） |
| STR006 | 文件超过 500 行 | 拆分为多个按主题聚焦的文件 |
| GEN001 | skill / rule 正文出现具体 URL | 抽象为占位符；项目级 URL 放 `docs/` 或 `framework/config/` |
| GEN002 | skill / rule 正文出现本地绝对路径 | 改为相对仓库根的路径 |
| GEN003 | skill / rule 正文出现哈希类名 | 升级到 P0 role 或 P1 text 定位 |
| GEN004 | skill / rule 正文出现业务术语黑名单词（`.claude/hooks/gate/wordlist.txt`） | 抽象为占位符或移入 `docs/`（仅提示） |
| REG001 | skill 未在 CLAUDE.md 路由表注册 | 在路由表新增一行 |
| REG002 | 路由表链接指向不存在的路径 | 修正链接或补上目标文件 |
| EVI001 | 在 `.claude/skills/` 或 `.claude/rules/` 下新建文件 | 按 P0.10 先提案（需用户确认，非错误） |
| EVI002 | 含 P 级条款但全文无 `**触发**：` 行 | 按 P0.9 补触发条件 |
| EVI003 | 条款内部无 `**触发**：` 行 | 补条款级触发行（仅提示） |
| EVI004 | 标题与既有条款高度重叠 | 按 P0.8 合并进原文件（仅提示） |
| PRV001 | 条款无 `**失败现象**：` 行 | 按 P0.11 写出这次实际观察到的错误表现 |
| PRV002 | 条款无 `**验证**：` 行，或验证里没有可核对的引用 | 给出用例 nodeid / 代码位置 / commit 短哈希 |
| PRV003 | 触发条件或失败现象是空话（`无` / `待补` / `视情况`）或过短 | 写出可复现的具体表现 |
| PRV004 | 验证引用的对象不存在（用例名、代码行、commit 查无此物） | 引用真实存在的对象；写不出说明尚未验证 |
| PRV005 | 已落库条款的证据链断了（引用的用例被删或改名） | 确认规则是否仍适用，更新引用或归档（仅提示） |
| PRV006 | 规则既无 `paths:` 也无人链接，永远不会被读到 | 登记进路由表、补 `paths:`，或删除（仅提示） |

存量条款由 `.claude/hooks/gate/baseline.json` 冻结豁免 PRV001–PRV004：设计这套检查时仓库里 45 个条款只有 5 个写了失败现象，强行回填只会逼人凭条款反推、编造一份看起来合规的假证据。**改写条款标题即视为新条款**，须补齐证据 —— 存量随日常维护自然收敛。重新冻结需 `--mode baseline --yes`，不要用它来绕过拦截。

## 闸门失效时

校验脚本遵循 fail-open：异常一律放行。所以**闸门没拦住不等于内容合格** —— P0.8/P0.9/P0.10/P0.11 是必须自觉遵守的规则，脚本只是兜底。

Write/Edit 之外的写入路径（Bash 的 `cat >`、`sed -i` 等）不触发 PreToolUse 闸门，由每轮结束时的 `Stop` hook 跑一次全仓扫描兜回来。Stop hook 只提示、永不阻塞：那里的退出码 2 意思是「阻止本轮停止」，与 PreToolUse 的 deny 完全不同，用错会把会话卡进停不下来的循环。
